# StageWrite AI 최종 기획 점검

## 최종 판단

현재 MVP 기획 기준에서는 핵심 플로우가 닫혔다.

사용자는 `요청 입력 -> 생성 조건 설정 -> 스토리 바이블/대본 생성 -> 음악 위치 추천 -> 음악 생성 mock -> 전체 리딩 mock -> 내보내기 -> 결제/크레딧 확인`까지 한 흐름으로 체험할 수 있다. 좌측 주요 페이지에는 모두 실제 화면이 있고, 문서화된 버튼은 빈 상태로 남아 있지 않다.

다만 상용 제품으로 판매하려면 아래 항목은 반드시 별도 기획/개발 범위로 잡아야 한다. 현재 공개 배포는 API 키 없는 정적 mock 제품이므로, 이 항목들은 MVP의 누락이라기보다 다음 단계의 필수 제품 범위다.

## MVP에서 닫힌 범위

| 범위 | 점검 결과 |
| --- | --- |
| 제품 형태 | 웹 우선 워크스테이션으로 결정. 노트북 중심 작가 작업에 맞음 |
| 첫 화면 | 마케팅 랜딩이 아니라 실제 작업실 진입 |
| 생성 조건 | 장르, 레퍼런스, 시간, 장면 수, 넘버 수, 인물 수, 무대 규모, 시대/공간, 목표/갈등, 톤, 대사/가사 스타일, 예산, 권리 기준 포함 |
| 스토리 바이블 | 로그라인, 시놉시스, 캐릭터, 구조, 씬 카드, 넘버 맵 포함 |
| 대본 생성 | 조건 기반 local generator와 API 교체 가능한 `generateDraft` 경로 분리 |
| 음악 위치 추천 | 오프닝, I Want Song, Reprise, 11시 넘버 등 뮤지컬 구조 기준 큐 생성 |
| 음악 생성 | OpenAI 프롬프트 재작성 경로와 음악 provider adapter, mock fallback 구현 |
| 전체 리딩 | Studio 플랜 가드, 캐릭터별 음성 캐스팅, voice provider adapter, mock fallback 구현 |
| 크레딧 | 플랜별 음악/리딩 크레딧, 사용 ledger, 부족 가드 구현 |
| 내보내기 | Markdown, Fountain, Manifest, PDF 인쇄 경로 구현 |
| 버튼/페이지 | 작업실, 기획 보드, 스토리 바이블, 넘버 보관함, 내보내기 센터, 결제/크레딧 모두 화면 존재 |
| 배포 | GitHub Pages 정적 MVP 배포 및 브라우저 검증 완료 |

## 상용화 전 필수 기획

| 항목 | 왜 필요한가 | 권장 우선순위 |
| --- | --- | --- |
| 계정/워크스페이스 | localStorage만으로는 유료 서비스, 장기 프로젝트, 여러 기기 작업을 지원할 수 없음 | P0 |
| 서버 저장소/버전 히스토리 | 작가에게 되돌리기, 초안 비교, 리딩 버전 관리가 중요함 | P0 |
| 실제 결제 checkout | 현재는 Stripe lookup key와 플랜 모델만 있음. 결제 생성/해지/영수증/웹훅 필요 | P0 |
| provider 작업 상태 추적 | 음악/음성 생성은 비동기 작업이 많으므로 queued, polling, failed, retry, callback 설계 필요 | P0 |
| 권리/약관/상업 사용 고지 | AI 음악/음성/레퍼런스 작품 사용은 저작권과 상업 사용 조건이 민감함 | P0 |
| 비용 한도/남용 방지 | Suno/voice 계열 API는 비용 폭주 가능성이 큼. rate limit, 월 한도, 실패 환불 규칙 필요 | P0 |
| 온보딩/설정 마법사 | 현재 설정 패널은 충분하지만, "글을 써줘" 입력 후 질문이 단계적으로 열리는 guided flow는 별도 개선 여지 있음 | P1 |
| 팀 협업/댓글 권한 | 뮤지컬은 작가, 작곡가, 연출, 제작자가 함께 본다. 공유 링크, 권한, 코멘트 thread 필요 | P1 |
| 대본 전문 포맷 | Fountain은 있지만 한국 공연 대본 PDF/Docx 스타일, 넘버 악보 메모, 무대 지시 인쇄 규칙은 추가 필요 | P1 |
| 캐릭터/넘버별 프롬프트 편집 | 실제 작가들은 곡별 가사, 모티프, 금지 레퍼런스를 세밀하게 고치고 싶어함 | P1 |
| 공개 마케팅 페이지 | 현재 앱은 작업 화면 우선이다. 유료 전환을 위해 별도 소개/가격/권리 안내 페이지가 필요함 | P2 |
| 모바일 보조 경험 | 첫 제품은 웹이 맞지만, 음악 데모 감상/코멘트 확인용 모바일 뷰는 추후 가치 있음 | P2 |

## 빠졌다고 보지 않는 항목

아래는 당장 MVP의 결함으로 보지 않는다.

- 네이티브 iOS/Android 앱: 타깃의 실제 집필 환경은 노트북/데스크톱이므로 웹 우선이 맞다.
- 실제 Suno/ElevenLabs 키 연결: adapter와 환경변수는 준비되어 있고, 키와 provider 계약이 있어야 완성된다.
- 마케팅 랜딩을 첫 화면으로 두는 것: 이 제품은 체험형 워크스테이션이므로 첫 화면이 작업실인 편이 더 설득력 있다.
- 완전한 공동편집: WriterDuet류 협업은 강력하지만 MVP에서는 댓글/저장/내보내기로 충분하다.

## 다음 단계 결론

다음 개발 라운드의 목표는 기능 추가보다 `상용화 기반`이어야 한다. 순서는 `계정/서버 저장 -> Stripe checkout/webhook -> provider job polling -> 권리/약관 고지 -> 버전 히스토리`가 가장 안전하다.
